# Прогноз розподілу найближчої виплати

Рішення власника 15.10.2026: **лише прогноз найближчої майбутньої виплати**.
Історичний розподіл, `payout_steps` і збереження факту до цього етапу не належать.

## Джерело

Чистий адаптер `projectionPayoutDistribution(pr, today)` у `index.html`.
Використовувати поточний `financeProjection` з реальною сьогоднішньою датою.
`pr.nextPlan.start > today`; повний запис `q` брати з `pr.periods` за цією
датою, `basis !== 'current'`. `projectionCore.next` та `nextPlan` не містять
усієї декомпозиції. Перемикання історичного періоду не змінює дату картки.
Активний кредитний сценарій явно позначати. Неповні дані — пояснення,
без нульових підстановок чи повторного додавання минулої зарплати.
Якщо `through` раніше виплати, `nextPlan` може існувати без запису q:
розподіл недоступний. Якщо запис q є, але прогноз не покриває день
`q.end - 1`, розподіл виплати доступний, проте агрегати кредитних витрат
і платежів усього періоду недоступні; не показувати їх як повні.

## Суми в цілих копійках

| Позначення | Поле / подія |
|---|---|
| O, власні перед виплатою | `q.openingCashCents` |
| P, виплата | `q.payoutCents`, звірка з `payout` цього дня |
| I, інші надходження дня | сума `income.amountCents` цього дня |
| A, покриття попередньої нестачі | сума `arrears.amountCents` цього дня |
| LR / LP / LS, розподіл залишку | `leftoverRepayCents` / `leftoverPrepayCents` / `leftoverSavingsCents` |
| N, після розподілу залишку | `q.ownCents` |
| R, резерв власних на обовʼязкові | `q.reserveCents` |
| PR, погашення кредиток із нового пулу | `q.payoutRepayCents`, включає Mono offset |
| PP, дострокове з нового пулу | `q.payoutPrepayCents` |
| F, власні понад резерв після розподілу | `q.availableCents - PP - q.monoOffsetCents` |
| B, план життя | `q.targetCents`, категорії й дні з `categories` / `schedule` |

Обовʼязкова перевірка збереження грошей:

```text
O + P + I = A + LR + LP + LS + N
N = R + PR + PP + F
q.leftoverCents = LR + LP + LS
q.repayCents = LR + PR
q.prepayCents = LP + PP
q.savingsCents = LS
F = q.cashOutCents + q.toMonoCents - q.monoOffsetCents
```

Бюджет B — використання частини F, не додатковий вихід грошей.
Показувати `min(B,F)` власних під план, `max(0,B-F)` нестачі на момент
розподілу та `max(0,F-B)` понад бюджет. Нестача не означає гарантований
кредит: подальші доходи й запозичення враховує календар прогнозу.
Прогноз кредитних витрат періоду — додатні `events[].debtDeltaCents`.
Непокриті платежі — `shortCents` / `dueShortCents`.

Розміщення F: `cashOutCents` та `toMonoCents - monoOffsetCents`.
Це план розміщення тих самих грошей, без створених переказів.
Резерв R не дорівнює автоматично всім обовʼязковим: він обмежений
власними коштами. Доступний кредитний ліміт не є джерелом виплати.
Рушій не повертає власний залишок на кожному рахунку чи джерело кожного
погашення окремої кредитки — не вигадувати такі деталізації.
Покриття попередньої нестачі A відбувається до розподілу залишку:
`leftoverCents` може бути меншим за O. Не вимагати `O = LR + LP + LS`.
Непогашену нестачу одразу після цього кроку брати з `arrearsAfterCents`
події `arrears`, а не з підсумку дня, який містить і подальші витрати.
Наявність LS не означає, що вже сплачено кожен майбутній платіж
розстрочки: найближчий може залишатися в резерві.

## Композиція

Компактна кнопка у заголовку наявного ForecastCard: ₴, «Прогноз» (або
«Сценарій») і дата. Повна назва та сума є в доступному підписі кнопки й
заголовку діалогу. Так заголовок лишається одним рядком на ПК, а графік
зберігає свою висоту. Повні кроки в діалозі:
залишок попереднього періоду → кошти після надходження → резерв,
погашення, власні після резерву → використання бюджету й розміщення.
За I > 0 або A > 0 назва групи «Кошти після надходжень і покриття нестачі».

Зберегти палітру, всі основні картки й мінімум графіка 180 px на низькому
ПК. Діалог: заголовок, Escape, фокус і повернення фокусу; телефон має
вертикальну композицію без горизонтальної прокрутки. Декоративна ₴:
одноразова transform/opacity 400–550 ms, aria-hidden, статична за
reduced-motion; остаточні числа видимі одразу.

## Верифікація

Окремі Node-тести адаптера й інваріантів; вузькі браузерні перевірки.
Синтетичні приклади: сьогодні виплата; вихідний; дві виплати одного дня;
інший дохід того ж дня; попередня нестача; залишок на кредитки,
розстрочки й заощадження; ручний бюджет 0 та понад власні; Mono offset;
дробові копійки; немає виплати; неповний горизонт; кредитний сценарій;
історичний період не змінює найближчу дату.

Геометрія 320/390 і 1280×800/860, клавіатура, reduced-motion.
Зміни ядра TS/Python та міграції БД для цього контракту не потрібні.

План підготовлено read-only архітектором за актуальними полями рушія.
Картку реалізовано у v160: 10 Node та 8 browser PASS; незалежне review
не виявило матеріальних проблем. У v159 картки ще не було.
Незалежна перевірка рушія: 18 доступних крайових прикладів, 3 стани
недоступності та 240 комбінацій параметрів Mono зберегли тотожності.
Додатний Mono offset у цих прогонах не виникав; його окрему формулу
перевіряти синтетично на виході адаптера, не видавати за приклад рушія.
