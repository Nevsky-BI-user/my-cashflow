# Перевірені розбіжності фінансової логіки

Дата перевірки: 10.10.2026. Лише локальний код і синтетичні значення; production, база та мережа не змінювалися. Це матеріал для погодження контракту розрахунків перед редизайном.

## 1. Фіксована зарплата: браузер і backend рахують різні виплати

Вхід: `rate=0`, `advance_amount=30000`, `salary_amount=40000`, дні виплат 21 і 6, `split_day=15`, дата перевірки 10.10.2026. Один дебетовий рахунок 100000, без боргів і зобовʼязань.

Очікувана узгодженість за поточною браузерною поведінкою: аванс 21.10.2026 = 30000. `index.html:192` явно підтримує фіксовані суми за відсутності додатної ставки.

Спостережено: витягнута з поточного `index.html` функція `salaryParts` повернула аванс 30000 і зарплату 40000; імпортований `periodBudget` із `supabase/functions/_shared/budget.ts` повернув аванс 0. Python-еталон теж повернув 0.

Причина: `budget.ts:31` не описує фіксовані суми, `budget.ts:163–170` та `scripts/budget_pool.py:125–132` завжди множать частку робочих днів на ставку. Висновок: підтверджена розбіжність реалізацій; власник має погодити підтримку фіксованого режиму або його вилучення.

## 2. Дата ручного запису: UTC може дати попередній місцевий день

Вхід: момент `2026-10-01T00:30:00+03:00`, середовище Node `TZ=Europe/Kyiv` (Node відображає канонічний alias `Europe/Kiev`).

Очікувана дата місцевого запису: 01.10.2026. Спостережено: місцеві компоненти Date дають `2026-10-01`, вираз `toISOString().split('T')[0]` дає `2026-09-30`.

Цей вираз встановлює дату транзакції (`index.html:724`, `:839`) і накопичення (`:740`, `:946`). Тому ранковий ручний запис за замовчуванням потрапляє в попередній день, а першого числа — у попередній місяць. Саме механізм дати відтворено в Node; браузерну форму в цьому прогоні не відкривали. Для timestamps на кшталт `created_at` ISO UTC доречний; висновок стосується календарного поля `date`.

## Відтворення та результати

Запуск із кореня репозиторію, після створення project `.venv`:

```powershell
.venv\Scripts\python.exe spec/.out/logic-audit/reproduce.py
git diff --check -- docs/redesign/logic-audit.md
```

Runner створює синтетичний JSON у вже ігнорованій `spec/.out/logic-audit/`, запускає `node spec/.out/logic-audit/reproduce.mjs` з `TZ=Europe/Kyiv` і Python-еталон `scripts/budget_pool.py <fixture> 2026-10-10`. Використовує актуальні browser-функції з `index.html`, а не переписані формули. Node v24.14.1; Python із project `.venv`.

Фактичний фінальний stdout:

```text
NODE {"browserAdvance":30000,"browserSalary":40000,"browserNextSalary":40000,"tsNextPayout":{"date":"2026-10-21","kind":"advance","amount":0},"timezone":"Europe/Kiev","localDay":"2026-10-01","formDefaultUtcDay":"2026-09-30"}
PYTHON {"nextPayout": {"date": "2026-10-21", "kind": "advance", "amount": 0.0}}
```

Обидві перевірки містять assertions і завершилися кодом 0. Перший запуск runner впав через Windows-кодування stdout дочірнього Python; одна локальна правка `PYTHONIOENCODING=utf-8` дала успішний повтор. Production-файли не редагувалися.

## Питання до власника, а не оголошені дефекти

- Часткова оплата: будь-яка expense з `fixed_id` зараз закриває весь платіж місяця. Чи потрібний залишок, повернення та явний місяць зобовʼязання?
- Перекази між власними рахунками, погашення кредитки й поповнення накопичень: як відділяти їх від доходів/споживчих витрат?
- Валюти й інвестиції: базова валюта, джерело/дата курсу, оцінка активів, ліквідність та склад чистих активів.
- Фактична зарплата проти плану: коли сьогоднішню виплату вважати зарахованою та як звʼязувати її з транзакцією без повторного доходу?

Жодне з цих правил під час перевірки не переозначувалося. Довготривалі процеси, сервери, DB-запити й зовнішні виклики не запускалися.
