# Контракт фінансового планування для редизайну

Погоджені правила власника та контрольні приклади, 10.10.2026. Це вимоги до майбутньої реалізації: поточне production-ядро не заявляється відповідним їм. Прототип `forecast-model.js` реалізує наведені нижче приклади одного періоду та перевірений через `node --test spec/forecast-model.test.cjs` (9/9). Валюта прикладів — гривня; інвестиції, курси й їх включення до чистих активів потребують окремого погодження.

## Погоджені правила

Статус реалізації: `nextPeriodPlan` у `_shared/budget.ts` і Python `next_period_plan`
реалізують базову формулу та денний розподіл; 13 синтетичних перевірок їхньої
відповідності пройдено. Інтерфейс і Telegram ще використовують попереднє ядро.
Позитивний `accounts.balance` означає власні гроші також на кредитному рахунку;
`credit_limit` до них не додається. Сценарій кредиту потребує явного `credit_ok`.

Період — між двома послідовними виплатами: `[дата наступної виплати; дата виплати після неї)`. Кінцева дата належить наступному періоду. Кількість днів — календарна різниця дат, без додаткового дня.

Базовий доступний плановий баланс:

```text
available = positiveOwnCash + nextPayout - mandatoryNextPeriod - fullCreditCardDebt
target = max(15000, available)
targetGap = max(0, 15000 - available)
plannedDailyVariableSpend = target / calendarDays
```

Власні гроші означають позитивні власні кошти, доступний кредит не додається до них. Повний кредитний борг віднімається один раз. Відʼємний available зберігається й показується як дефіцит. Мінімальна ціль 15000 не підмінює actual available: показуємо обидва числа, цільовий gap і касові розриви.

Майбутній прогноз щодня віднімає plannedDailyVariableSpend з каси. Розподіл між категоріями визначають ваги зі сторінки «Бюджет». Якщо коштів бракує, прогноз показує відʼємну касу/розрив; він не стискає витрати до наявної каси мовчки. За відсутності ваг сума явно показується як «Не розподілено».

Для досягнення цілі можна запропонувати явно придатні обовʼязкові платежі перенести на кредитку. Сценарій показує суму перенесення, новий борг, доступний ліміт і дату майбутнього погашення. За відсутності відомої придатності чи підтвердженого ліміту сценарій не вважається доступним. Платежі не переносимо автоматично.

Будь-яка привʼязана до постійного платежу витрата закриває його зобовʼязання за місяць своєї дати фактичною сумою: після оплати 1000 для планового 5000 цей місяць закрито, залишок 4000 не створюється. Факт уже рухає баланс відповідного рахунку; планову суму цього місяця прибираємо. Заборонено повторно віднімати і план, і факт. Наступний місяць знову має планове зобовʼязання. Повернення й оплата кількох місяців одним записом потребують окремого правила.

## Контрольні приклади, обчислені незалежно від ядра

| Випадок | Вхід/дія | Очікування |
|---|---|---|
| База | власні 2800 + виплата 50000 − обовʼязкові 28000 − борг 16000 | available 8800; target 15000; gap 6200 |
| Повний кредитний сценарій | з обовʼязкових 6200 придатні; ліміт достатній | касовий план 15000; **новий борг 6200**; базові 8800 лишаються видимими |
| Частковий сценарій | можна перенести лише 4000 | касовий план 12800; новий борг 4000; gap до цілі 2200 |
| Без сценарію | придатність/ліміт невідомі або платежів немає | available 8800; target 15000; gap 6200; прогноз показує касовий розрив |
| Вище мінімуму | 2800 + 50000 − 10000 − 16000 | available і target 26800; gap 0; витрати 1675/день за 16 днів |
| Відʼємний план | 2800 + 10000 − 28000 − 16000 | available −31200; target 15000; gap 46200; явний дефіцит, сценарій перевіряється окремо |
| Нульова каса сьогодні | сьогодні 0, наступна виплата 50000, обовʼязкові 28000, борг 16000 | план наступного періоду 6000; сьогоднішня каса 0; майбутні кошти не показуються як доступні зараз |

Повний кредитний сценарій збільшує касовий план лише на перенесений платіж, не створює дохід і не збільшує чисті активи. На дату погашення прогноз зменшує касу та борг на 6200. Наступний період має врахувати цей борг і нове повторюване зобовʼязання наступного місяця без дублювання одного погашення. Дата погашення визначається погодженим правилом кредитки; випадок, де вона настає всередині поточного горизонту, може знову створити розрив.

## Дні, категорії та копійки

Для `[2026-10-21; 2026-11-06)` маємо **16 днів**. Ціль 15000 означає **937,50/день**. Приклад ваг, а не заміна налаштувань користувача:

| Категорія | Вага | За період | Середнє за день |
|---|---:|---:|---:|
| 1 | 40% | 6000 | 375 |
| 2 | 20% | 3000 | 187,50 |
| 3 | 15% | 2250 | 140,625 |
| 4 | 10% | 1500 | 93,75 |
| 5 | 10% | 1500 | 93,75 |
| 6 | 5% | 750 | 46,875 |

Гроші зберігаємо й підсумовуємо цілими копійками; середня сума не означає однакову округлену суму кожного дня. Пропозиція алгоритму: методом найбільших залишків розподілити periodTotal між категоріями за вагами, потім кожну категорію між днями; рівні залишки розвʼязувати стабільно за id категорії та датою. Для категорії 3: 8 днів по 140,63 і 8 по 140,62 = 2250; для категорії 6 — протилежний порядок 46,87/46,88 дає 750 і дозволяє зберегти загальні 937,50 щодня в цьому прикладі. Інваріанти: сума категорій = target; сума всіх денних сум = target; жодних загублених копійок. Загальний алгоритм не повинен обіцяти ідеально однакову денну суму, якщо total не ділиться на days.

## Пропозиція, що ще потребує підтвердження

Для минулих днів і поточного дня фактичні змінні витрати замінюють нарахований денний план; для майбутніх днів використовуємо тільки план. Факт не віднімається вдруге поверх уже врахованого денного плану й похідного балансу. Потрібне підтвердження власника щодо неповного поточного дня: відняти лише факт або залишити прогноз невитраченої частини добового бюджету.

## Верифікація арифметики

Незалежна перевірка через Python Decimal/datetime, без запуску фінансового ядра:

```powershell
.venv\Scripts\python.exe -c "from decimal import Decimal as D; from datetime import date; n=(date(2026,11,6)-date(2026,10,21)).days; a=D(2800)+D(50000)-D(28000)-D(16000); t=max(D(15000),a); print(n,a,t-a,a+D(6200),t/n); print([t*D(w)/100 for w in [40,20,15,10,10,5]]); print(a+D(4000),t-a-D(4000))"
```

Спостережено: `16 8800 6200 15000 937.5`; категорії `6000, 3000, 2250, 1500, 1500, 750`; частковий сценарій `12800 2200`. Команда завершилася кодом 0. Це контрольні очікування, а не свідчення відповідності production-реалізації.
